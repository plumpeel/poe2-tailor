# 评测基准：BD 低配答案

> **这是整个项目说服力的地基。**
>
> 每个 BD 手工写一份「我认为合理的低配方案」。之后用它来验证工具的输出对不对——
> 没有这个基准，"我的工具能降配"就只是一句话，面试官无法判断真假。
>
> **目标：W0 完成 1 个，W2 完成 5 个。**

---

## 怎么写一条基准

对每个 BD 填下面这些字段：

| 字段 | 说明 |
|---|---|
| BD 名称 / 来源 | 哪个构筑（poe.ninja 链接 / 自己配的 / 工会里的） |
| 原版预算 | 大约多少 D（神圣石） |
| 核心机制 | 这个 BD 靠什么打伤害（一句话） |
| **不能动的东西** | 哪件装备 / 哪个机制动了就崩 |
| **可以降配的位置** | 哪些位置是"锦上添花" |
| 低配方案 | 换什么、预算降到多少 |
| 强度损失估计 | 你判断掉多少（凭你的游戏经验，写个范围） |
| 你的信心 | 高 / 中 / 低（不确定的地方标出来） |

**"不能动"和"可以降配"这两栏是最值钱的**——它们直接把你的游戏经验变成了可检验的数据。

## 工具跑完之后怎么用这份基准

| 对比项 | 说明 |
|---|---|
| 工具给出的低配方案 vs 我的答案 | 差在哪？是它傻，还是我想错了？ |
| 工具估计的强度损失 vs 我的估计 | 差多少？差距大的地方就是模型的薄弱点 |
| 工具漏掉的"不能动" | 最严重的错误类型——会导致用户 BD 直接崩 |
| 工具找到的我没想到的替代 | **这是亮点，写进 README 的效果对比** |
